# DockHop 设计方案

> DockHop 是 [docker_migrate](https://github.com/lx969788249/docker_migrate)（bash 版）的 Go 重写版，换了新名字、放在独立的仓库，和旧版互不兼容。
> 状态：已复核，决定见第 7 节；下文的“现有版本”“bash 版”都指 docker_migrate。
> 依据：逐个文件通读了 `src/` 全部 8356 行代码、全部测试和 README，并在两台服务器上做了三项实验（见第 2 节）。

---

## 0. 一页结论

1. **现有版本有 7 个会直接影响用户的问题**（第 1.1 节）。其中 2 个是“迁移显示成功，实际丢了东西”：独立容器的显卡、停止等待时间、`-it` 等配置会丢；单服务的 Compose 项目（Vaultwarden、Memos 这类）不会迁移 compose 文件。另有 2 个是程序被强制结束后，两台服务器都可能停在半途、没人收拾。
   这些问题大多出在结构上（把配置翻译成命令行参数、恢复逻辑写在迁移包里），在 bash 里修补成本高，正好在 Go 版本里从根上解决。
2. **核心思路**：DockHop 是脱胎于 bash 版的新项目，继承它好的体验（一行命令、大白话、分步骤显示、预检、失败回滚），不背旧接口的包袱（命令、环境变量、链接都重新设计，更简单）；内部换成：
   - 直接调用 Docker 接口，**把原来的容器配置原样交给 Docker 重建**，而不是翻译成 `docker run` 参数；
   - **Compose 项目整体迁移**，用用户原来的 compose 文件启动；
   - 数据读写走 Docker 接口，**不再需要 alpine 辅助镜像**，新服务器不用连 Docker Hub；
   - 迁移包只放数据，**恢复逻辑全部在程序里**，永远是新服务器上的最新版；
   - 下载支持**断点续传**，旧服务器能看到下载进度，恢复成功后**自动结束传输**；
   - 两台服务器上**被强制中断的任务，下次运行时能发现并还原**。
3. **关键假设已在真机上做了八项实验**（Docker 20.10 和 29.2、老 docker-compose 1.29 和 Compose v5，见第 2 节），其中：
   - 通过 Docker 接口读写卷数据，属主、权限、软链接、特殊文件都原样保留；
   - 把容器原始配置直接交给另一个版本的 Docker 重建，包括显卡、`-it`、停止等待时间等现在会丢的配置，全部一致；
   - 用 digest 固定版本的镜像（Immich 等应用的写法）迁移后，新服务器离线时用不了——现有版本就有这个问题（C14），已有解决办法；
   - 加密选定开源库 age，链接从约 330 个字符缩短到约 100 个；Compose 用原文件重建后标签和源端完全一致。
4. **不兼容旧版**：Go 版只认自己的迁移包格式，不读 bash 版的包，代码里没有任何为旧版保留的分支。切换前一直用 bash 版，Go 版两端都做完、验收通过后一次性切换。用现有的 8 个真实应用测试作为验收标准，预计实际工作 5–7 天。
5. **已经确定的 7 个决定**列在第 7 节。

## 1. 现有版本的不足

### 1.1 直接影响用户的问题（按严重程度）

| # | 问题 | 后果 | 位置 |
|---|---|---|---|
| A1 | 独立容器重建时**这些配置不会迁移**：`--gpus`（显卡）、`--stop-timeout`、`--stop-signal`、`-it`、`--pids-limit`、`--oom-score-adj`、`--userns`、`--cgroup-parent`、`--link`、`--volumes-from`、MAC 地址、挂载传播方式、卷的 subpath / nocopy、tmpfs 挂载参数 | 迁移显示成功，但 Jellyfin/Immich/Ollama 丢了显卡；数据库的停止等待从自定义值变回 10 秒，关机时可能来不及写盘；依赖 `-it` 的程序（部分游戏服务器）行为改变 | `templates/run.sh` 只翻译了它认识的参数 |
| A2 | **只有一个容器的 Compose 项目被当成独立容器**，只选了项目中部分服务时也一样 | compose 文件不会迁移。Vaultwarden、Memos、Uptime Kuma 这类最常见的单服务项目，迁移后在新服务器上没法再用 `docker compose pull/up` 升级。README 写的“Compose 配置恢复到原工作目录”对它们不成立 | `backup/flow/20-select.sh:118`、`30-metadata.sh:76`；CI 日志里 uptime-kuma 恢复显示“0 个 Compose 项目” |
| A3 | **新服务器上的恢复被强制中断（kill -9、内存不足被系统结束、断电重启）后没有任何补救** | 回滚记录还在磁盘上，但下次运行不会发现它：新服务器上原有的服务可能一直停着，或者被改名成 `xxx.docker-migrate-backup-1234`。1G 内存的机器（如 138）被系统结束进程是现实风险 | `templates/restore/tx-*.sh` 只处理程序还活着时收到的信号 |
| A4 | **旧服务器上的备份被强制中断后，停掉的容器不会被拉起** | 停了哪些容器只记在内存里；进程被 kill -9 或机器重启后，这些容器一直停着（`docker stop` 过的容器，`unless-stopped` 也不会自动启动） | `backup/flow/10-setup.sh` 的 `STOPPED_ON_BACKUP` |
| A5 | **备份前没有检查磁盘空间**，打包放在当前目录 `./bundle` | 在小分区里运行时，可能在**容器已经停机的时候**把磁盘写满；当前只在加密前检查一次 | `50-package.sh:168` |
| A6 | 新服务器恢复**必须能从 Docker Hub 拉到 alpine:3.20**（用来读写数据卷） | 国内服务器、内网机器常常拉不下来，恢复在第 7 步失败 | `templates/restore/flow.sh:92` |
| A7 | **下载不支持断点续传** | 跨国传几个 GB 的包，中途断一次就从头下载（curl 的重试也是从头来） | `backup/flow/60-serve.sh` 的 Python 服务没有处理 Range |

### 1.2 结构问题（是上面这些问题的根源）

| # | 问题 | 说明 |
|---|---|---|
| B1 | **容器配置靠“翻译成命令行参数”来重建** | Docker 的配置项很多，命令行表达不了全部（例如多段入口命令），每漏一项就悄悄丢一项（A1）。Docker 以后加的新配置也不会被迁移 |
| B2 | **恢复逻辑一部分写在迁移包里** | 每个独立容器的 `runs/<名字>.sh` 是旧服务器生成的。新服务器即使是最新版，重建容器的逻辑仍然取决于旧服务器的版本（刚修的入口命令问题，旧服务器不更新脚本就用不上） |
| B3 | **备份主流程是 6 个依次执行的大脚本，靠 23 个全局表传数据** | 哪一步用什么数据看不清，没法单独测试；“配置有问题却在停机后才报错”就是这样来的（已修） |
| B4 | **同一段逻辑写了好几份** | 拆分 Compose 配置文件名 4 份、等健康检查 3 份、读容器网络 3 份，修一处漏一处 |
| B5 | **同一份配置反复解析** | 295 处调用 jq、34 处 docker inspect，每次都起一个新进程把同一份 JSON 读一遍 |
| B6 | **拼凑多种外部工具，每种都有后备分支** | Python（7 段内嵌程序）、openssl、jq、curl、tar、gzip/pigz、ss/netstat、busybox、nc；有 Python 和没有 Python 走两条不同的路径，下载服务有三套实现（netcat 那套连随机路径都没有） |
| B7 | **进程之间靠文件和环境变量通信** | 日志、失败原因、警告、阶段耗时各用一个旁路文件，阶段编号通过环境变量传给子脚本 |
| B8 | **错误处理靠 `set -e`、trap、子 shell** | 之前修过的“错误输出被永久关掉”“bash 4.0 下 trap 里变量丢失”“`--diagnose` 输出被截断”都是这套机制本身的坑 |

### 1.3 体验和次要问题

| # | 问题 |
|---|---|
| C1 | 旧服务器看不到新服务器的下载进度；恢复完成后要用户回到旧服务器手动按回车 |
| C2 | 恢复失败时，**解密后的明文数据**（数据库文件等）保留在 `~/docker_migrate_restore`（bash 版）里“便于排查”，没有提示这是敏感数据 |
| C3 | 新服务器要“下载一份 → 解密再写一份 → 解压再写一份”，磁盘要 3 倍空间，低配机器慢（138 上 45MB 解密花了 17 秒） |
| C4 | 卷和目录先压成 `.tgz`，整个包又压缩一次，CPU 白白多花一倍；而且卷的压缩发生在**停机期间**，拖长停机时间 |
| C5 | 迁移后用户的 Compose 目录里多出 `_resolved_config.yml`、`_migration_images.yml`、`_env_files/` 等内部文件；容器标签指向解析后的文件而不是用户的 `compose.yml`。Compose 项目的 `build:` 上下文目录不会迁移，迁移后 `docker compose build` 会失败 |
| C6 | 会自动用包管理器安装 jq、python3、openssl 等，等于改动了用户的系统；Docker 没运行时会尝试 `nohup dockerd`，擅自启动守护进程 |
| C7 | 端口检查依赖 `ss` 命令，没有就不检查；迁移包里两个容器互相占用同一个端口时不检查；源端本来就停着的容器有端口映射时会误报冲突 |
| C8 | 日志脱敏只认 `名字=值` 的写法，`"Password": "xxx"` 这种 JSON 写法不会被隐藏 |
| C9 | 两台服务器网络不通时没有办法：不能把迁移包用别的方式（scp、网盘）带过去再恢复 |
| C10 | 交互菜单直接回车会选中全部容器，包括检测到的面板管理容器 |
| C11 | 数据卷的**标签**不迁移：Compose 创建的卷到了新服务器后，Compose 会提示它“不是由 Compose 创建的”，`docker compose down -v` 也不会再管它 |
| C12 | 端口绑定在某个具体 IP（如 `1.2.3.4:80`）而新服务器没有这个 IP 时，预检不会发现，创建容器时才失败 |
| C13 | 不识别 Swarm 管理的容器，会把它们当成普通独立容器迁移 |
| C14 | **用 digest 固定版本的镜像**（如 `redis:6.2@sha256:…`，Immich 官方 compose 就这样写）：迁移包里虽然带了镜像，但新服务器加载后**既找不到 digest、也找不到标签**，只能重新从仓库拉。新服务器连不上 Docker Hub 时恢复失败（实验 3 已确认，见第 2 节） |

### 1.4 值得保留的设计（Go 版照搬）

- 恢复的**事务**：先登记再改动，失败按记录逆序还原，最后一步才提交。这是整个工具最有价值的部分。
- **迁移前预检**和“只提示 / 需要选择 / 无法继续”三级分类，以及每类问题的选项文字。
- **链接里带密钥**、加密加签名、下载前先拿迁移计划的设计。
- 备份时**有改动才做快照**、系统路径只重建挂载不迁移内容、软链接目录的处理、容器依附关系的自动纳入和恢复顺序。
- 9 个步骤的显示、大白话的报错和建议、成功删日志失败留日志。
- 测试，尤其是只看结果的 `tests/apps/`。

## 2. 已经验证的技术前提

在两台服务器上做了实验（只用 `dmtest_` 资源，已全部清理）。搬瓦工是 **Docker 20.10**（API 1.41），138 是 **Docker 29.2**（API 1.53），正好覆盖“从很旧的 Docker 迁到最新 Docker”。

**实验 1：通过 Docker 接口读写卷数据。** 创建一个**不启动**的容器挂载卷，用 Docker 的“容器文件归档”接口读出卷内容，再写进另一个不启动容器挂载的新卷。两个版本上结果相同：

- 属主（1234:5678、999:999）、权限（640）、软链接、FIFO 特殊文件全部原样保留；
- 不需要镜像里有 tar，也不需要启动容器，任何本地已有的镜像都能用来创建这个临时容器。

→ Go 版读写卷数据不再需要 alpine，新服务器不用连 Docker Hub（解决 A6）。

**实验 2：把容器原始配置直接交给另一个版本的 Docker 重建。** 用接口创建一个带有“现在会丢失的配置”的容器（显卡请求、`-it`、停止信号和等待时间、多段入口命令、进程数限制、OOM 优先级、init、nocopy 卷、tmpfs 参数、sysctl、健康检查），把它的原始配置交给另一台服务器的 Docker 创建：

- 20.10 → 29.2、29.2 → 20.10 **两个方向都创建成功**，新版本 Docker 导出的配置里旧版本不认识的字段会被忽略；
- 上面列出的所有配置在新容器里**完全一致**。

同时发现一个必须处理的细节：有些字段是 Docker 自己按版本填的默认值。例如容器里默认隐藏的系统路径清单，20.10 是 10 条、29.2 是 12 条。如果原样传过去，旧服务器的清单会被“固定”在新服务器上，新版本多出来的保护就没了。所以重建前要去掉一份明确的“Docker 自动填写的默认值”清单（见 3.4.1）。

**实验 3：用 digest 固定版本的镜像。** 在 20.10 上按 `busybox:1.36.1@sha256:…` 拉取并 `docker save`，到 29.2 上 `docker load`：加载成功，但用 digest 引用和用标签都找不到这个镜像，禁止联网时创建容器失败。原因是旧格式的镜像导出文件里没有仓库清单，digest 无法在本地还原。→ 这是现有版本就有的问题（C14），Go 版的处理见 3.4.12。

### 2.1 第 0 阶段补充验证（2026-10-21）

两台服务器都是 x86_64、2 核；搬瓦工 2G 内存、Docker 20.10、老的 Python 版 docker-compose 1.29；138 只有约 220MB 可用内存、Docker 29.2、Compose v5.0.2。只用 `dmtest_` 资源，已全部清理。

**实验 4：选定加密实现。** 每种方案各处理 512MB 模拟数据（一半可压缩、一半像已压缩的镜像层）：

| 方案 | 搬瓦工 | 138 | 峰值内存 |
|---|---|---|---|
| bash 版的 AES-CTR + HMAC（参照） | 288 MB/s | 101 MB/s | 10MB |
| age 格式（ChaCha20-Poly1305 分块） | 387 MB/s | 104 MB/s | 10MB |
| 自己实现 ChaCha20-Poly1305 分块 | 381 MB/s | 82 MB/s | 12MB |
| 自己实现 AES-256-GCM 分块 | 415 MB/s | 106 MB/s | 12MB |
| zstd 多核压缩 + age 加密整条流水线 | 318–364 MB/s | 58–65 MB/s | 19–29MB |
| zstd 一边压缩一边解压 | 323 MB/s | 67 MB/s | 29–41MB |

（数字里包含生成测试数据本身的开销，实际只会更快。）

→ **选定 age**：速度和自己实现的一样，是广泛使用、经过审计的开源库，自带截断和乱序检测；不用自己维护加密代码。连同 zstd，程序只有 3.4MB。内存占用在几十 MB 以内，138 这种低配机器也毫无压力。

**实验 5：Compose 用原文件重建。** 在 Compose v5 上启动一个项目，记下标签后删除容器和卷，按记录**带标签**预先建卷，再用原文件、原项目名启动：
- 新容器标签和原来**完全一致**，卷标签也完全一致，Compose 没有任何提示；
- 对照：卷不带标签（bash 版现在的做法）时，Compose 提示 `volume "…" already exists but was not created by Docker Compose`，确认了 C11；
- `docker compose config --hash` 算出的值和容器标签里的配置摘要一致；启动时如果用了 shell 里临时设置的变量（`TAG=v9 docker compose up`），两者就不一致。
  **更正（第 2 阶段实测）**：服务用了 `env_file` 时，即使文件完全没改，两者也不一致（Compose v5 和 v2.38 都是这样），这个实验没覆盖到。所以改为直接核对按现在的文件算出的镜像和环境变量与运行中的容器，见 3.4.2。

**实验 6：digest 固定的镜像（补充实验 3）。**
- Docker 29 的新镜像存储导出再导入后，镜像内容完好（镜像 ID 就是原 digest），但用“名字@digest”仍然找不到，新旧 Docker 情况一样；
- 加载后再按 digest 拉取一次，**只下载了清单、没有重新下载任何层**，代价很小。→ 3.4.12 的“先加载、再按 digest 补清单”可行。

**实验 7：一次连接多个网络。** Docker 20.10（API 1.41）创建容器时带两个网络会被拒绝（HTTP 400），29.2 可以。→ 按 3.4.1：老版本先连主网络，创建后再连其他网络。

**实验 8：断点续传和链接长度。** Go 标准库的下载服务原生支持断点续传：中断后带 Range 再请求，返回 206，续传部分和前半段拼起来与原文件一致。用 age 的密钥，链接示例：

```
http://203.0.113.7:8080/k3Jx9QmP2vLa/#a7j8zg6qtzkg8ddwxnzl94th3c4ns7ckdzjxu0w0fypeapduldmqq2q4nn
```

共 96 个字符（bash 版约 330 个），密钥能完整还原。

### 2.2 第 3 阶段实测发现（2026-10-21）

迁入做完后在两台服务器上实测，发现几处 Docker 本身的行为和设计时的假设不同，已经按下面的方式处理：

| 发现 | 处理 |
|---|---|
| Docker 29（containerd 存储）`docker commit` 出来的镜像，`docker save` 只导出清单，没有配置和内容；加上 `--platform`、和原镜像一起导出、走接口导出都一样，加载后的镜像无法使用 | 不再用“commit + 导出快照镜像”迁移容器里的改动，改为只迁移改动的文件（3.4.1） |
| 同样在 containerd 存储里，容器记的镜像 ID 是多平台镜像的 ID，按这个 ID 创建容器会选错平台（报“读不到配置”） | 迁入时一律按镜像名创建容器；回滚重建时名字和 ID 都试 |
| 新版 Docker 的 `docker diff` 会把为挂载创建的空目录（包括 `--tmpfs`）、`--init` 放进去的 `/sbin/docker-init` 算作改动 | 这些不算改动（`spec.LayerChanges`）；以前每个带挂载的容器都会被当成“有改动” |
| 写入卷数据的接口加上 `copyUIDGID` 时，所有文件会被改成容器用户的属主（不是保留原属主） | 不加这个参数，tar 里记录的属主原样保留 |
| `docker commit` 会把临时容器的入口命令写进镜像，`ENTRYPOINT []` 这样的指令也盖不住 | commit 时在请求里明确给出原镜像的入口命令（空的给空列表） |
| 老的 docker-compose 1.x 把 `-f` 的写法原样记在标签里（相对路径），Compose v2 记绝对路径 | 迁出时记下 `-f` 的原样写法，迁入时照原样传 |

### 2.3 第 4 阶段真机迁移（2026-10-21）

用两台服务器上的真实服务各迁了一次（迁完核对数据后删掉新服务器上的副本）：

| 服务 | 方向 | 结果 |
|---|---|---|
| cdt-monitor（单服务 Compose，SQLite 卷） | 搬瓦工 Docker 20.10 → 138 Docker 29 | 成功，停机不到 1 秒，迁入 19 秒 |
| waline（Compose：MongoDB 数据目录 493MB + 匿名卷） | 138 → 搬瓦工 | 第一次：搬瓦工只有老的 docker-compose 1.29，读不懂配置里的 `$/`，自动还原；装上新版 Compose 后用同一个链接重试成功（不用重新下载），205 条评论一致，停机 38 秒 |
| umami（Compose：PostgreSQL 卷） | 138 → 搬瓦工 | 成功，数据完全一致，停机 38 秒 |

发现并修复的问题：
- 镜像里本来没有 `/sbin` 时，`--init` 让 Docker 新建了 `/sbin`，被误判成容器里的改动（只排除了 `/sbin/docker-init` 本身）。
- waline 容器里积攒了 6.6GB 崩溃转储（`/app/core.*`），停机期间全部打包，停了约 10 分钟才被手动中断（中断后两个容器自动恢复）。现在停机前先统计容器里改动的大小、计入磁盘检查，超过 100MB 时提醒（按决定只提醒、不拦）。
- Compose 报错时只保留了最后几行，看不到真正的错误；现在从报错那一行开始取。新服务器只有老的 docker-compose 而旧服务器用的是新版时，检查时提前提醒，失败时说明怎么装新版。
- 停机不到一秒时显示“停机不到 1 秒”，不再显示“0 秒”。

连不上旧服务器（138 的 ufw 只放行 22/80/443）时，15 秒内说明“连接超时”，并提示安全组和 `ufw allow 8080/tcp`；放行后用同一个链接继续。

## 3. Go 版本设计

### 3.1 原则

1. **新项目，不背包袱**：继承 bash 版好的体验——一行命令、大白话、分步骤显示、迁移前预检、失败自动回滚；命令、环境变量、链接、迁移包格式都按“最简单好用”重新设计，不为和 bash 版一致而妥协。
2. **配置原样搬运，少做翻译**：能直接用 Docker 原始数据的地方就不转换。
3. **只依赖 Docker**：除了 Docker 和（有 Compose 项目时的）`docker compose`，不需要任何其他命令，也不往系统里装软件包。
4. **任何中断都能收场**：两台服务器上所有“改动前”的状态都写到磁盘，程序被强制结束后下次运行能还原。
5. **先报告再动手**：所有能提前发现的问题，在停机或改动任何东西之前报告。

### 3.2 用户能看到的部分

**运行**：仍然是一行命令，不带参数时显示菜单：

```bash
bash <(curl -fsSL https://dockhop.run)
```

```
1. 迁出
2. 迁入
```

**命令**：用子命令代替一堆开关。中文叫“迁出 / 迁入”，方向一看就懂，“迁入”也自然包含恢复；英文命令对应 `out` / `in`，和项目名连起来读就是 “dock hop out / dock hop in”。bash 版叫“备份 / 恢复”，容易让人以为是备份工具。屏幕上的步骤标题和结果摘要也统一用“迁出 / 迁入”。

| 命令 | 用途 | 对应 bash 版 |
|---|---|---|
| `dockhop out` | 迁出（旧服务器）：选择容器、打包、提供下载 | `--backup` |
| `dockhop in [链接]` | 迁入（新服务器）：预检、下载、恢复 | `--restore=URL` |
| `dockhop version` | 显示版本 | — |

v1.1.4 精简掉了 `check`（`in` 本来就先检查，有问题在改动之前停下）、`diagnose`（失败时保留的日志里记着系统和 Docker 的情况）和 `in --file` 离线迁入（只有旧服务器在内网时才用得上，手动拷文件又麻烦），见第 7 节第 10 条。

通过一行命令运行时，参数接在后面即可，例如 `bash <(curl …/run.sh) in '链接'`。

**选项**：用户会主动选择的东西做成命令选项，环境变量只留给少数全局设置（附录 B 有和 bash 版的完整对照）：

| 选项 | 用途 |
|---|---|
| `out --port 端口`、`out --host 地址` | 下载服务的端口（默认 8080，被占用自动后移）、链接里的地址（默认自动探测） |
| `out --include a,b` | 只迁移指定的容器（或它们所在的 Compose 项目），不显示菜单 |
| `out --stop-shared` | 非交互运行时，允许临时停止和所选容器共用数据的其他容器 |
| `in --yes` | 非交互运行时，预检发现的问题自动采用推荐做法 |
| `in --existing replace\|skip\|fail` | 新服务器已有同名服务时：替换（失败时放回原来的）/ 跳过 / 停止；不写时询问，`--yes` 时替换 |
| `in --keep-succeeded` | 有服务没能启动时不提问，保留已经正常运行的、只删除没启动的（默认全部删除，见 3.4.6） |

v1.1.4 精简掉了 `out --no-stop`、`out --snapshot`、`out --workdir`（和 `DOCKHOP_HOME` 重复）、`in --skip-check`、`in --health-timeout`、`in --keep-files`、`-v`/`--verbose` 和 `DOCKHOP_KEEP_LOG`（测试用的改名为 `DOCKHOP_TEST_KEEP_LOG`）。

**环境变量**：

| 变量 | 默认 | 用途 |
|---|---|---|
| `DOCKHOP_HOME` | `~/.dockhop` | 日志、中断记录、回滚资料、锁和工作文件都放在这里（`logs/`、`state/`、`rollback/`、`work/`），不再散落在家目录的几个地方；系统盘不够大时换到别的盘 |
| `DOCKHOP_NO_STATS` | — | 不统计、也不显示成功完成迁移的次数（也认 `DO_NOT_TRACK=1`） |
| `DOCKHOP_MIRROR` | — | `run.sh` 下载程序用的镜像站 |

**屏幕输出**：保留 bash 版的风格——分步骤、每步一行、`✓` / `✗`、进度条、警告汇总、结果摘要、失败时给出原因/建议/日志位置；文字按需要重新斟酌，不要求和 bash 版逐字相同。

**链接**：从约 330 个字符缩短到约 100 个，只包含地址和一个密钥，见 3.4.13。

### 3.3 代码结构

```
cmd/dockhop/             程序入口
internal/
  cli/        参数和环境变量、模式选择、帮助文字
  ui/         阶段行、进度条、警告汇总、结果摘要、提问（交互 / 非交互）
  logging/    日志文件、脱敏
  docker/     精简的 Docker 接口客户端：本机 socket、版本协商、原始 JSON 透传
  spec/       容器配置“原样重建”：去掉自动默认值、按预检决定改端口/IP、依附顺序
  compose/    调用 docker compose：读配置、启动、等待健康
  bundle/     迁移包读写、文件清单和校验
  crypto/     加密、签名、链接解析
  transfer/   下载服务（断点续传、进度、完成通知）和下载客户端
  backup/     选择容器、读取配置、停机、快照、打包；中断记录
  preflight/  预检和“恢复决定”
  restore/    恢复事务：准备、数据、网络、Compose、容器、回滚、提交、中断补救
  host/       磁盘空间、端口、对外地址、CPU 架构、权限
run.sh        一行命令的入口脚本（约 30 行）
```

- 第三方依赖只有几个：加密库 age、zstd 压缩库（klauspost/compress，纯 Go）、终端处理（golang.org/x/term）、读 Compose 文件用的 YAML 库（gopkg.in/yaml.v3）。**不引入 Docker 官方的 Go 客户端**：它依赖很多、体积大，而且它的类型定义会丢掉比它新的 Docker 版本才有的字段，违背“原样搬运”。我们只用到二十来个接口，自己写一个薄客户端更合适。
- 每个包都能单独测试；备份和恢复都改成“函数 + 明确的数据结构”，不再有全局表（解决 B3、B4、B5、B7、B8）。

### 3.4 关键设计决定

#### 3.4.1 容器重建：原始配置透传（解决 A1、B1、B2）

**现在**：把 inspect 结果翻译成 `docker run` 参数，漏一项丢一项。
**改为**：把源容器的原始配置（`Config`、`HostConfig`、网络设置）作为 JSON 直接交给新服务器的 Docker 创建容器，只做以下明确的修改：

| 修改 | 原因 |
|---|---|
| 去掉主机名（等于容器 ID 前 12 位时） | 那是 Docker 自动起的，新容器有新的 ID |
| 去掉 Docker 按版本自动填的默认值：`MaskedPaths`、`ReadonlyPaths`（未用 `systempaths=unconfined` 时）、`CgroupnsMode` / `IpcMode`（等于源端默认时）、`Runtime=runc`、`ConsoleSize`、`Isolation`、日志设置（等于源端 Docker 默认时） | 让新服务器按自己的默认值走，不把旧服务器的默认值固定下来（实验 2 发现的问题）。源端默认值记录在迁移计划里 |
| 按预检决定改端口、改为自动分配 IP、不再对外开放、改绑到所有地址 | 现有功能；“改绑到所有地址”对应 C12 |
| `container:<ID>` 改为 `container:<名字>` | 依附的容器在新服务器上有新 ID |
| 镜像名已经指向别的版本（或已删除）时，改用容器实际用的旧版本镜像（`dockhop-image:<ID 前 12 位>`） | 现有功能 |
| 容器里删除过文件时，镜像改为带改动的镜像（`dockhop-image:<容器名>`，在新服务器上做出来） | 见下面“容器里的改动” |
| 只保留用户指定的静态 IP 和 MAC；动态分配的不固定 | 现有规则 |
| Docker 25 以下不支持创建时连接多个网络：先连主网络，创建后再连其他网络 | 兼容老版本（20.10 已确认是 API 1.41） |

匿名卷（镜像声明、没有名字的卷）：容器创建后找到 Docker 新建的那个卷，把迁移过来的数据写进去，不再按原编号建卷。

**容器里的改动**（实现时调整，见 2.2）：迁出时按 `docker diff` 只打包新增和修改的文件（新增的目录整个算一项），删除的路径记成清单；运行时目录、挂载点、Docker 自己管理的文件不算。迁入时容器创建之后、启动之前把文件写进去，容器的镜像名不变（以后照常升级）。只有删除过文件时，才在新服务器上用临时容器做出一个带改动的镜像。

另外加两项**预检**：容器要显卡（`DeviceRequests`）而新服务器没有 NVIDIA 运行环境时停下说明；要求的设备不存在时停下说明（现有）。

恢复顺序除了现有的 `container:` 依附关系，也考虑 `--link`、`--volumes-from` 引用的容器（被引用的先建）。

数据卷连同**标签**一起重建（C11）。Swarm 管理的容器在菜单里标出、默认不选，并说明不支持（C13）。

**测试**：恢复后把新容器的完整配置和源容器逐字段比较，除上表的修改外必须一致。现有的保真测试扩展成这种全量比较，不再只抽查几个字段。

#### 3.4.2 Compose 项目整体迁移（解决 A2、C5）

- **选中项目里任何一个服务，就迁移整个项目**，菜单上显示项目名，后面标出容器数（“site  [2 个容器]”），不显示项目目录。单服务项目也按 Compose 项目迁移。
  （Compose 项目本来就应该作为一个整体管理，“只迁一半”会让项目在两边都不完整。是否这样做需要你确认，见第 7 节。）
- **用用户原来的 compose 文件启动**，项目名、工作目录、`-f` 文件列表和源端完全一样；迁移后容器标签和源端一致，用户以后照常在原目录 `docker compose pull && docker compose up -d`。
- **迁移整个项目目录**（不只是几个固定文件名），这样 `build:` 上下文、`env_file`、`extends`、`include` 引用的文件都在。以下内容排除：已经作为挂载目录迁移的子目录（避免重复）、单个超过 100MB 的文件（提示用户）。项目目录外被引用的文件（绝对路径的 `env_file` 等）通过 `docker compose config` 找出来，一并迁移到原路径。
- **迁出时核对配置是否还对得上**：用 `docker compose config` 按现在的文件算出每个服务最终的镜像和环境变量，和正在运行的容器逐项核对。不一致说明启动后改过文件，或启动时用了 shell 里临时设置的变量——迁过去会和现在不一样。（不用 `config --hash`：服务用了 `env_file` 时它和容器标签对不上，会误报。）提示用户：`取消，我先在项目目录执行 docker compose up -d，让运行的容器和文件一致（推荐）/ 仍然迁移，迁入后按现在的文件启动`；不能提问时给出警告并继续。
  （实现时调整：原计划的“把实际生效的配置做成覆盖文件带过去”需要从容器反推 Compose 配置，容易出错，改为让用户先让两者一致。）
- 项目目录以外引用的文件（`-f` 指定的配置文件本身，`env_file`、`build` 上下文、`configs`、`secrets`、`include`、`extends`）**直接读原始的 Compose 文件**找出来。不用 `docker compose config` 的输出：不同版本差别很大，新版会把 `env_file` 并进环境变量、不再列出路径，加了 `--no-env-resolution` 也不一定保留。为此引入一个 YAML 库（gopkg.in/yaml.v3）。
  实现时补充：`include`、`extends` 引用的文件接着读，里面的相对路径按 Compose 的规则从那个文件自己的目录（或 `project_directory`）算起，`include` 默认读的 `.env` 也算；找出来的路径互不包含（目录里的文件不再单独列出），否则同一个文件打包两次，迁入时整个包会被拒绝；路径里有变量的确定不了，迁出时提醒用户自己处理（`include` 的 `project_directory` 用变量时也是，v1.1.8 起；以前悄悄按被包含文件的目录算，可能漏掉文件也不提醒）。
- 新服务器上调用已安装的 `docker compose`（插件）或独立的 `docker-compose`（v2）。源端用老的 Python 版 docker-compose（v1）启动的项目照样能识别和迁移，只是新服务器上要有 v2；容器名会从 v1 的 `项目_服务_1` 变成 v2 的 `项目-服务-1`，预检时提示。
- 不再往用户目录里写内部文件。服务需要换镜像时（容器里删除过文件、digest 镜像改用迁移包里的），通过启动时额外加一个临时的 `-f` 覆盖文件实现，这个文件放在程序自己的工作目录里，用完删除；以后从这台服务器再迁出时，找不到这个文件不算缺失。容器里新增和修改的文件在 `up --no-start` 之后、启动之前写进去，不需要换镜像。
  v1.1.6 起镜像只承载删除：新增和修改的文件不管独立容器还是 Compose 容器，都在创建后按容器分别写进去。覆盖文件是按服务写的，同一个服务的几个副本只能用同一个镜像，所以镜像里只删每个副本都删过的文件；只有部分副本删过的，在别的副本里还在，不能删，删过的副本里就会重新出现，迁入时明确提示。以前把每个副本的改动连同删除一起做成镜像、再按服务覆盖，最后一个副本的镜像会被所有副本用上，其他副本的改动静默丢失（审查发现）。
- `-f` 按旧服务器上的原样写法传（实现时补充，见 2.2），只启动旧服务器上有的服务（`up --no-start 服务名…`，profiles 里的服务也照此处理）。
- 每个容器恢复成旧服务器上的状态。`docker compose start` 会把一个服务的全部容器、连同它依赖的服务一起启动，所以只有项目的容器原来全部在运行时才用它；有停着的容器（例如同一个服务一个副本在运行、一个停着）时，按 `depends_on` 的顺序逐个服务启动原来在运行的容器，等它们就绪再启动依赖它们的服务。顺序里还要加上借用网络、`--link`、`--volumes-from` 的关系（v1.1.8 起）：老的 docker-compose 1.x 读不出 `depends_on`，以前这时会先启动借用别人网络的服务而失败。
- **项目之间的创建和启动顺序**（v1.1.5 加入，v1.1.6 改为按依赖的强弱分别处理）：同一组里的每个 Compose 项目、每个独立容器是一个“启动单位”。单位之间的依赖分三种：
  - **要先存在**：用的网络是另一个迁入的 Compose 项目建的（交给 Compose 按那个项目的文件创建），或者 `--volumes-from` 另一个容器。只决定创建的先后。
  - **要先就绪**：借用另一个容器的网络、进程、IPC 命名空间，或者 `--link` 它。Docker 要求被依赖的先在运行，所以它先启动、就绪了才启动用到它的；它起不来，用到它的不启动。
  - **最好先就绪**：从配置里认出来的，容器的环境变量的值或启动命令里，有一个词正好是同一个网络上另一个容器的名字或网络别名（不分大小写）。被认出来的先启动、等它就绪；但这是猜的，可能认错（某个词碰巧和别的容器同名，甚至方向反了），所以等不到时不拦着：接着启动后面的，它最后再等一次（完整的时间再多 1 分钟，Docker 自动重启的间隔最长 1 分钟）。
  先按“要先存在 / 要先就绪”的顺序把全部容器创建好，再按“要先就绪 / 最好先就绪”的顺序启动；互不相关的不互相等，全部启动之后再一起确认就绪。最坏的情况（猜的都不对）和服务器重启时一样：所有服务一起起来，靠应用自己重试，或者 Docker 按重启策略重启它。日志里记下每条依赖的种类和原因（只写变量名，不写值）。
  起因：1Panel 的每个应用是一个 Compose 项目，接在同一个 `1panel-network` 上，Halo 的启动参数里写着数据库的服务名（`r2dbc:pool:postgresql://postgresql:5432/halo`）。v1.1.4 及以前按项目名一个一个“启动并等就绪”，先启动的 Halo 找不到还没启动的数据库，等到超时，整个迁入回滚。v1.1.5 把认出来的依赖当成了必须等到的门槛，认错时可能卡住（审查发现）；创建也还是“项目在前、独立容器在后、项目之间按名字”，一个项目用另一个项目建的网络（反向代理的常见写法）、或者借用独立容器的网络时会创建失败。v1.1.6 改成上面的样子。
- **等多久**（v1.1.5 加入，v1.1.6 算上每次检查本身的时间）：有健康检查的，最多等到 Docker 按容器自己的设置判它“不健康”的时候再多 30 秒，至少 60 秒、最多一小时。Docker 在启动宽限期过后、连续 retries 次没通过才判不健康；每次检查最多花 timeout，检查完再隔 interval 才做下一次，所以最晚是“启动宽限期 + retries ×（interval + timeout）”（没写的按 Docker 的默认值）。中途不健康、在重启都接着等（小机器上启动慢，或者要等它连的服务），通过了马上往下走。
  v1.1.4 及以前只等到第一次检查跑完：Halo 是 95 秒，而 Docker 自己要三四分钟才下结论。没有健康检查的，等它稳定运行几秒、不在反复重启，最多 60 秒。容器退出了、Docker 也不再重启它时（会重启的，状态是“正在重启”），马上算失败。

#### 3.4.3 数据读写不依赖辅助镜像（解决 A6）

- **卷**：按实验 1 的方式，用迁移涉及的镜像创建一个不启动的临时容器挂载这个卷，通过 Docker 接口读写。不需要 alpine、不需要联网。
  清空卷（替换已有的卷、回滚）时接口没有删除功能：启动一个临时容器，把 DockHop 程序本身挂进去运行删除（程序是静态编译的，任何镜像里都能运行）。
- **宿主机目录**：程序直接读写本机文件（权限不够时按 3.4.11 提权）。恢复时仍然先解到同级的临时目录、再原子替换，旧目录保留到提交（现有做法）。
- Docker 不在本机（`DOCKER_HOST` 指向远程）时，宿主机目录无法正确处理：预检时说明并停止。

#### 3.4.4 新的迁移包格式（解决 C3、C4、A5）

| | 现在（bash） | Go 版 |
|---|---|---|
| 压缩 | 卷、目录各自 gzip，整包再 gzip 一次 | 整包只压缩一次，用 zstd（压缩和解压都比 gzip 快几倍，多核并行） |
| 旧服务器磁盘 | 先写一份未加密的目录，再写一份加密包，约 2 倍 | **边打包边压缩边加密，直接写成最终文件**，约 1 倍（压缩后大小） |
| 新服务器校验 | 下载完再把整包读一遍算摘要和签名 | 每 64KB 一段，下载的同时逐段校验；包损坏或被篡改，在出问题的那一段就能发现 |
| 停机时间 | 停机期间每个卷、目录单独 gzip 一次 | 停机期间只做一次快速压缩（zstd 多核），通常读盘速度就是上限；镜像导出仍在恢复容器之后（现有做法） |
| 新服务器磁盘 | 下载 1 份 + 解密 1 份 + 解压 1 份 | 下载 1 份 + 解压 1 份，解压完删掉下载文件 |
| 包内容 | 数据 + 恢复脚本 | 只有数据和配置记录，没有脚本 |
| 长度未知的数据 | 先写成文件再打进包 | 卷数据、镜像导出这类事先不知道大小的数据流，按固定大小（如 16MB）分段写进包里，内存占用固定，也不用先落盘 |
| 加密和链接 | AES-256-CTR + HMAC-SHA256，链接约 330 个字符 | 分块认证加密（age），链接约 100 个字符，见 3.4.13 |

打包前先估算大小（卷、目录、镜像），在**停机之前**检查工作目录所在磁盘的空间，不够就提示换目录（`DOCKHOP_HOME`），绝不在停机后才发现磁盘满了（解决 A5）。

**不兼容旧版**：Go 版只读写自己的格式，不读 bash 版的迁移包，也不为旧版保留任何代码分支。

- 迁移是一次性的操作，两台服务器都通过一行命令拿最新版，实际不会出现“一边新一边旧”；
- 唯一的例外是切换当天有人用旧脚本在旧服务器打了包：新服务器看到 `.tar.gz.enc` 结尾的旧链接时，只给一句明确的提示——“这个链接是旧版生成的，请在旧服务器重新运行一行命令”，不做任何解析。

#### 3.4.5 传输：断点续传、进度、完成通知（解决 A7、C1）

- 下载服务支持断点续传；新服务器下载中断后自动从断点继续，已下载部分会重新核对。
- 旧服务器显示 `新服务器正在下载 ██████░░ 62% · 8.1MB/s`，下载完成后显示“新服务器已下载完成，正在恢复……”。
- 新服务器恢复结束后通知旧服务器（用链接里的密钥签名，别人伪造不了）：
  - 成功：旧服务器显示“新服务器已恢复成功”，自动关闭下载服务、清理、结束；
  - 失败：旧服务器提示“新服务器恢复失败，下载服务继续保留，处理后可以重新粘贴链接”。
  - 仍然可以随时按 Esc 再按回车手动结束（v1.1.3 起；以前是输入 q 回车，q 现在也还能用）。
- 新增 `--file=/path/迁移包`：两台服务器网络不通时，用 scp、网盘等方式把迁移包带过去，再用同一个链接（提供密钥）恢复（解决 C9）。它同时取代现在“手动解压迁移包后运行包里的 `restore.sh`”的用法（新格式的包里没有脚本）。**v1.1.4 去掉了**：只有旧服务器在内网时才用得上，手动拷文件、敲长命令和“不想麻烦”相反（第 7 节第 10 条）。

#### 3.4.5a 停机（实现时补充）

- **借用要停止的容器网络、进程空间的容器也一起临时停止**（如借用 VPN 容器网络的 sidecar）：被借用的容器一停，它们的网络就断了，重启后也不会自己接回去。bash 版漏了这种情况，第 2 阶段的验收测试发现的。
- **分批同时停止**：依赖别人的容器在前一批，被依赖的在后一批，同一批同时停。停机时间取决于最慢的一个，而不是全部加起来（测试里 4 个容器从 62 秒降到 30 秒左右）。恢复时按相反的顺序。
- 下载服务端口不再在迁出时提问，用 `out --port` 指定，被占用时自动往后找。

#### 3.4.6 中断补救（解决 A3、A4）

- **旧服务器**：停机前把“停了哪些容器、原来是什么状态”写到 `~/.dockhop/state/`。任务正常结束会删掉；如果程序被强制结束，下次运行（任何模式）开头会提示：
  `上次备份被中断，有 2 个容器还停着：nextcloud-app、nextcloud-db。现在启动它们吗？[Y/n]`
- **新服务器**：恢复事务的记录改为一个追加写入的日志文件（每一步改动前先写一条）。下次运行开头如果发现没完成的事务：
  `上次恢复在第 8 步被中断，新服务器上有 3 个原有容器被暂停或改名。现在还原到恢复前的状态吗？[Y/n]`
  选择还原就按日志逆序执行回滚（和现在程序内回滚是同一套代码）。v1.1.8 起，开始还原之后按 Ctrl+C 也做完再退出（和这次迁入失败时的回滚一样），没能还原的地方列在结果里，不再当成“什么都没改动”的取消、删掉日志；旧服务器恢复停下的容器也是开始了就做完。
  实现时补充：日志在 `~/.dockhop/rollback/current/`，每一条写入后立即落盘；最后一行写了一半（断电）时忽略那一行。还原分三遍：先删除新建的容器，停下又在运行的原有容器（包括上次还原已经放回、重建的原有 Compose 容器，它们的 ID 变了，按名字找），删不掉、停不下就停下，不动数据；再还原网络、Compose 文件、目录、数据卷；最后放回原有的服务：旧容器改回原名并重新连上网络（拿回固定 IP），重建原有的 Compose 容器（按它们的原始配置原样重建，不依赖原来的 Compose 文件；被借用网络的先建，彼此之间按旧 ID 的引用改成按名字），全部放回之后再按依赖统一启动原来在运行的（包括临时停下的）。v1.1.8 起排序跨项目、跨独立容器：以前按日志一条一条地放回、启动，一个项目借用另一个项目的容器的网络时，可能先重建、启动借用的那个而失败。每一步都可以重复执行，还原到一半再被中断，下次从头还原一遍也是安全的。写下“已提交”之后不再还原。
- **只有一部分服务起不来**（v1.0.3 加入）：用户界面上不再说“还原”（容易理解成“恢复迁移过来的数据”），统一说“删除这次迁入的内容”“把被替换的原有服务放回原处”。
  - 开始改动之前，先用新服务器上的 Compose 对每个项目执行 `config -q`（项目目录解到临时目录里；报错涉及临时目录里没有的文件、项目目录以外的文件、绝对路径时不算数），读不懂就停下，什么都没改。项目目录在某个挂载目录里（例如服务挂载了 `./`）时，项目文件随挂载目录迁移，迁移包里没有单独的项目目录：v1.1.6 起迁出时把 Compose 读配置要用的文件（`-f` 的文件、`.env`、`env_file`、`include`、`extends` 等）另外打包一份给检查用。以前这种项目在空的临时目录里检查，必然报“读不懂”，没法迁入（审查发现）。
  - 要迁入的服务按“能不能分开”分组：同一个 Compose 项目、共用数据卷或目录（含项目目录所在的挂载目录、项目目录以外的同一个文件；路径按新服务器上解析软链接之后的实际位置比较）、共用自定义网络、借用网络 / `--link` / `--volumes-from` 的容器在同一组；临时停止的已有容器跟着它用到的数据所在的组。日志里每条记录带组号。
  - 一组起不来时接着启动其他组。全部起不来就全部删除；只有一部分起不来时问用户：全部删除（默认、推荐，环境最干净），或者只删除起不来的组。选项里写明保留的代价：已经运行的服务可能依赖起不来的服务、看起来在运行实际用不了；起不来的要再迁一次；最后决定不迁了要自己删。不能提问时全部删除，`--keep-succeeded` 时保留。
  - 只删除一部分时：先恢复保留下来的组临时停下的容器；把日志改写成只剩起不来的组的记录（之后被强制结束，下次运行只会删除它们）；按日志删除它们；再清理保留下来的组的回滚资料。已经迁入的容器名和新 ID 记在 `~/.dockhop/state/in-<链接编号>.json`，用同一个链接重试时，容器还在、ID 没变就跳过（Compose 项目的容器少一个就整个项目重迁），全部迁入后删除这个记录。旧服务器收到 `partial`，提示只迁入了一部分，继续提供下载。

#### 3.4.7 预检（解决 C7，并去掉 Python）

逻辑和问题分级、选项文字保持不变，用 Go 重写，另外：
- 端口检查：直接尝试监听这个端口，再结合 Docker 接口里的端口占用，不依赖 `ss`；
- 迁移包里多个容器之间互相冲突的端口也检查；
- 源端本来就停着的容器不检查端口（恢复后它也不启动）；
- 新增显卡检查（见 3.4.1）、Docker 不在本机的检查（见 3.4.3）；
- 新增：端口绑定的具体 IP 在新服务器上不存在时，作为“需要选择”的问题，选项是“改为绑定到所有地址（推荐）/ 不对外开放 / 取消”（C12）。

#### 3.4.8 恢复事务

保留现有设计：准备（记录并暂停/改名已有的同名服务、共享数据的容器）→ 恢复数据 → 网络 → Compose → 独立容器 → 健康检查 → 提交。改动：
- **检查全部在改动之前，改动全部在事务里**（v1.1.6）：解开迁移包之后、改动任何东西之前，按新服务器现在的样子决定替换、保留哪些已有服务，找出要临时停下的、和迁入的数据共用的容器，并确认要停下的容器都能停下再恢复——用 `--rm` 启动的一停就被 Docker 删掉、Swarm 的任务停了会被换成新的，都不行（迁出时停机打包用的是同一条规则）。“迁入的数据”包括数据卷、挂载目录，也包括 Compose 项目目录和项目目录外的文件：保留的已有容器用着它们时不能迁入。然后才开始事务；加载镜像也在事务里：镜像名被改之前记下它原来指向哪个镜像，失败时改回去，原来没有的名字删掉（这次迁入进来、已经没人用的镜像跟着删掉）。以前镜像在事务开始前就加载、加名字，迁入失败后新服务器上原有的同名镜像名仍指向旧服务器的版本（审查发现）。v1.1.8 起：加载镜像之前记下这台服务器原有的镜像；回滚时先把镜像名全部改回去，最后只删这次迁入带来的、没有名字也没人用的镜像，原有的一个不删（以前改回一个名字就按 ID 删它原来指向的镜像：原有的镜像只剩一个别的名字时会被连名字一起删，两个名字互换了指向时后面那个改不回去）。只保留一部分服务时，没保留的组单独用的镜像名也改回去。
- **替换、保留哪些已有容器，预检和迁入共用一条规则**（v1.1.8）：迁移包里的 Compose 项目对应新服务器上同名项目的全部容器，单独迁入的容器对应同名的已有容器（不管它属不属于某个 Compose 项目）；对应的部分迁入就替换它，跳过就保留它。以前预检认为属于别的项目的同名容器不会让出端口，平白给迁入的容器换了端口，选择保留它时也漏查共用数据。加载镜像可能要好一会儿，改动已有的服务之前再看一次：和这次迁入有关的容器（要替换的、要临时停下的）有新建、启动、停下或被重建（例如被 Watchtower 更新）的，就停下，不按过时的情况停容器、写数据。
- 回滚要靠的东西都确实写到磁盘（v1.1.6）：事务日志每条写入后落盘，日志文件本身所在的目录也落盘；数据卷、目录的备份写完先落盘，才去清空、替换原来的；迁出的停机记录同样。以前备份只写进了缓存，断电后可能只剩半份，而原件已经被替换了。停机记录读不懂时保留并说明，不再当作没有删掉。
- 记录格式从多个 `.tsv` 文件改成一个日志文件，便于中断后补救（3.4.6）；
- 健康检查等待时间按每个容器自己的检查设置计算（v1.1.5 起等到 Docker 自己判它不健康的时候再多 30 秒，见 3.4.2）；
- 恢复失败时：**删除解密后的数据，保留加密的下载文件和日志**。重试不用重新下载，磁盘上也不留明文数据（解决 C2；需要你确认，见第 7 节）。只有重试也用不上的下载文件才删掉：迁移包本身的内容有问题（解不开、有不合规的内容），或者要写的目录会盖住 DockHop 自己的目录（要换 DOCKHOP_HOME，下载的文件也会放到别处）。
- 不在服务器上留没用的东西（v1.1.7 起）：锁文件只在拿着锁时存在（放锁前先删，拿到锁后确认还是那个文件）；复制给临时容器挂载的程序（`bin/dockhop-helper`）迁入结束就删；成功、或者还没改动就取消时删掉日志，成功时连同一种任务以前失败留下的日志一起删；最后删掉空了的子目录，DockHop 的目录空了也删掉。用新链接迁入时删掉以前的链接留下的下载和记录，迁出开始时删掉以前被强制结束留下的工作目录。以前迁移成功后还会留下空目录、锁文件和一份约 9MB 的程序，只是打开看看再取消也会留下日志。“还没改动就取消”看的是用户有没有按 Ctrl+C（context 有没有取消），不看被打断的那一步返回什么错误；被打断的那一步的失败只写日志，不显示成“✗ …失败”（v1.1.8 起；1.1.7 在检查环境、识别容器时按 Ctrl+C，会显示成“已中断”并留下日志）。

#### 3.4.9 日志和诊断（解决 C8）

- 位置、文件名、成功删除失败保留、`--verbose`、`--diagnose` 都保持（v1.1.4 起去掉了 `--verbose` 和 `diagnose`：日志开头记下系统和 Docker 的情况，失败时附上日志就够了）；
- 等容器就绪时（v1.1.5）不记每秒一次的查询，只记状态的变化、每次健康检查的结果（检查命令的输出）、容器的重启和退出码。
  没能就绪时，先把容器最后 100 行输出写进日志再回滚（回滚会删掉容器，之后用 `docker logs` 就看不到了）。报错里接上最能说明问题的一行（跳过 Java 等的调用栈）；按名字找不到别的服务时，建议里说出是哪个名字。
  以前只留最后 5 行、报错里接最后一行，Java 应用报错时正好是一行调用栈，看不出原因；建议里的 `docker compose logs` 在回滚之后也用不了。
- 脱敏改为**按值隐藏**：程序知道每个容器的环境变量，凡是名字像密码/密钥/令牌的，它的值无论以什么形式出现在日志里都会被替换；链接里的密钥同样按值替换。比按写法匹配可靠。

#### 3.4.10 不再改动用户系统（解决 C6）

- 不再安装 jq、python3、openssl 等，Go 版用不到；
- Docker 没安装：给出官方安装命令，不自动安装（装哪个版本应该由用户决定；需要你确认，见第 7 节）；
- Docker 没运行：提示 `systemctl start docker`，不再擅自启动 dockerd；
- 新服务器缺少 `docker compose` 而迁移包里有 Compose 项目：预检时停下说明（现有）。

#### 3.4.11 权限

能访问 Docker 就能完成大部分工作。只有读写宿主机目录时当前用户没有权限，才用 `sudo` 提权（会提示输入密码），和现在一样。不一律要求 root，避免影响 rootless Docker 的用户。

#### 3.4.12 digest 固定的镜像（解决 C14）

- 备份时记录每个镜像“引用名 → 镜像 ID”的对应关系；
- 预检时（下载迁移包之前）对这类镜像用 Docker 的“查询仓库信息”接口确认能否按 digest 拉取，这个接口只查询、不下载；
- 能拉取：恢复时加载迁移包里的镜像后，再按 digest 拉取一次补上仓库清单，和源端完全一致；已加载的层不会重复下载，只拉一个清单（实验 6）。新服务器本机已经有这个摘要的镜像（原来就有，或者已经按摘要拉下来了）时直接用，不再去仓库拉（v1.1.6）；
- 不能拉取：作为预检里“需要选择”的问题：`改用迁移包里的镜像（推荐，内容和旧服务器完全相同，只是配置里的镜像名去掉 @sha256 部分）/ 取消`。选择后把加载的镜像打上不带 digest 的标签，容器和 Compose（通过临时覆盖文件）使用这个标签。

#### 3.4.13 链接和加密（新设计）

bash 版的链接带着摘要、加密方式、128 位十六进制密钥、IV、签名，约 330 个字符，复制时容易漏掉一截（bash 版专门有“链接不完整”的报错）。DockHop 改为：

```
http://203.0.113.7:8080/k3Jx9QmP2vLa/#a7j8zg6qtzkg8ddwxnzl94th3c4ns7ckdzjxu0w0fypeapduldmqq2q4nn
```

- 共约 100 个字符（bash 版约 330 个）；`#` 后面只有一个密钥（age 的 X25519 私钥，32 字节），迁移包和迁移计划都用它加密；
- `#` 后面的部分浏览器和 curl 都不会发给服务器，下载服务本身拿不到密钥（和现在一样）；
- 加密改用成熟的“分块认证加密”（每 64KB 一段，每段都带校验，能发现截断和顺序被调换），不再自己拼“加密 + 签名”。**选定开源加密库 age**（实验 4：速度和自己实现一样，经过审计，不用自己维护加密代码）；
- 迁移计划用同一个密钥加密，地址由链接推算（现有设计）；v1.1.6 起迁移计划是必须的：迁出时生成失败就停下，迁入时没有它就不迁（以前会跳过全部检查、直接替换同名服务）；
- 下载的每个文件（迁移包、单独的镜像文件）按迁移计划里记的大小下载，多一个字节就停下、删掉（以前一直写到对方停止发送，网络上的设备可以把磁盘写满）；用之前按记下的 SHA-256 核对（v1.1.6 起）。同一次迁移的文件用的是同一把密钥，解密只能发现内容被改坏，发现不了被换成同一次迁移的另一个完整文件；迁移计划和清单都经过认证，按它们记的校验值核对才能确认拿到的就是那个文件。核对通过后解开时仍发现内容有问题，说明旧服务器上的迁移包本身就有问题，重新下载还是同一个文件，所以提示在旧服务器重新迁出。1.1.6 之前的旧服务器没有记录校验值：镜像文件有好几个，被对调了发现不了，v1.1.8 起可能要从旧服务器下载镜像时，下载之前就停下，提示在旧服务器上用新版重新迁出（迁移包只有一个，没有可以对调的，照常用）；
- 识别到 bash 版的旧链接（`.tar.gz.enc#sha256=…`）时，只提示“这个链接是 docker_migrate 生成的，请在旧服务器改用 DockHop 重新运行”。

#### 3.4.14 安装和发布

- `run.sh`（约 30 行）：判断 CPU 架构（x86_64 / arm64 / armv7）→ 从 GitHub Releases 下载对应程序 → 核对 SHA-256 → 运行 → 删除。
- 国内访问 GitHub 慢：程序同时发布在 Gitee 和 GitHub 上（v1.1.3 起，发布时 `scripts/gitee-release.sh` 自动同步到 Gitee）。先从哪个下载：`dockhop.run` 返回 `run.sh` 时按访问者在不在中国大陆填上 `PREFER`（中国大陆是 Gitee，其他地方包括港澳台是 GitHub；国家是 Cloudflare 本来就给每个请求标好的，不另外查，也不记录），`run.sh` 直接从那里下载压缩包；没有填（从别处拿到的 `run.sh`）时先同时从两边各下载 2 秒比一比，从快的那个下载。比速度这 2 秒以前每次都要等（实测海外合计约 2.2 秒、国内约 4.9 秒），直接下载后海外约 0.2 秒、国内约 2.9 秒。15 秒内平均不到 20KB/s 或失败时换另一个，新地址支持时从断开的地方接着下载（GitHub 支持，Gitee 不支持、只能从头下载）。也支持 `DOCKHOP_MIRROR=镜像地址`（设置后只用它）。程序的校验值写在 `run.sh` 里，从哪里下载都能确认没被篡改。以前的 Cloudflare 中转（`dockhop.run/v版本号/…`）已经去掉，`dockhop.run` 只返回 `run.sh` 和迁移次数。
- 成功完成迁移的次数（v1.1.2 加入）：迁入成功后程序向 `dockhop.run/count` 发一个空的 POST，Worker 在 D1 里把唯一的一个数字加 1（只认 `DockHop/` 开头的 User-Agent，同一个地址一分钟最多算 5 次）；开头的菜单显示这个数字（v1.1.9 起满 20 次才显示：次数还少时不显示，满了照常显示真实的次数，不改数字）。只有正式发布的版本访问，`DOCKHOP_NO_STATS=1` 或 `DO_NOT_TRACK=1` 时不访问；连不上、出错时不显示、不报错。v1.1.7 起：从国内访问 `dockhop.run` 常常要好几秒（实测 2.5～14 秒），以前菜单最多等 1.5 秒去读，国内基本显示不出来；“加一”在结果显示完才发、只等 3 秒，国内大约一半没算上。现在一行命令下载 `run.sh` 时，Worker 顺便把次数填进脚本里预留的 `COUNT=""`（1 秒内读不到就不填），`run.sh` 用 `DOCKHOP_COUNT` 交给程序，菜单直接显示，不再单独请求；直接运行程序时才去读，最多等 1.5 秒。“加一”在迁入提交成功时就在后台发出，和收尾（删除临时文件、通知旧服务器、显示结果）同时进行，退出前最多等 10 秒。
- 发布：打标签后 GitHub Actions 自动编译三个架构、生成校验值、发布，再同步到 Gitee（上传和 GitHub 上一样的文件，只保留最近 10 个版本：Gitee 每个仓库的附件合计不能超过 1GB）。从 GitHub 的服务器往 Gitee 上传很慢（实测每秒十几到几十 KB，还会断，一个版本要半小时左右），所以 `run.sh` 要用的压缩包先传，已经传好的文件不重传，长时间没有进展的上传自动重试。同步失败不影响 GitHub 上的发布，可以手动运行 gitee 工作流接着同步。更新说明（v1.1.6 起）写在附注标签里：第一行是一句话摘要，空一行之后是几条简短的说明，放到 GitHub 和 Gitee 的发布页上。
- 版本号从 1.0.0 开始（第 7 节）。

## 7. 已经确定的决定

1. **Compose 项目整体迁移**：选中项目里任何一个服务，就迁移整个项目。
2. **不兼容旧版**：Go 版不读 bash 版的迁移包，bash 版也读不了 Go 版的包；旧链接只给一句提示（v1.1.4 起不再特别识别，按链接格式不对处理）。
3. **恢复失败时**：删除解密后的数据，保留加密的下载文件和日志（重试也用不上的下载文件除外，见 3.4.8）。
4. **恢复成功后旧服务器自动结束传输**，也可以随时按 Esc 再按回车结束（只按回车不会结束，免得误触；v1.1.3 之前是输入 q 回车）。
5. **Docker 没装时**只提示官方安装命令，不自动安装。
6. **镜像继续随迁移包传输**；“不打包镜像、新服务器在线拉取”以后再考虑。**v1.1.4 起改为**：每个镜像单独导出成一个加密文件（迁移包格式版本 2），新服务器在下载之前逐个决定——本机已经有一模一样的（镜像 ID 或仓库摘要相同）就直接用；能从镜像仓库（或本机配置的镜像加速）按摘要拉到就自己拉，拉完加上原来的名字；都不行才从旧服务器下载。拉取失败、卡住或太慢（一分钟进展不到 3MB）时自动改从旧服务器下载。按摘要拉到的一定是同一个镜像，compose 文件里的 `postgres:latest` 这类写法不用改；容器里改过的文件不在镜像里，照旧从旧服务器传。整个过程不显示、不提问，只写日志。新版本迁入时仍能读格式版本 1 的迁移包（镜像在包里）；老版本迁入时会提示把新服务器上的 DockHop 更新到最新版。顺带：迁入启动 Compose 时加 `--pull missing`（Compose 支持时），配置里写了 `pull_policy: always` 的服务不会被换成仓库里的新版本，连不上镜像仓库时也不会因此失败。
7. **版本号**：DockHop 是新项目，从 1.0.0 开始。切换后 docker_migrate 仓库保留，README 顶部指向 DockHop；约一个月内只修严重问题，之后归档（只读）。
8. **名字和仓库**：项目改名 DockHop，命令名 `dockhop`，代码放在独立的新仓库 `lx969788249/dockhop`，和旧仓库隔离。
9. **当作新项目设计**：命令改为子命令：迁出 `out`、迁入 `in`、检查 `check`、诊断 `diagnose`（名字由你定），用户的选择做成命令选项，环境变量只留 `DOCKHOP_HOME`、`DOCKHOP_KEEP_LOG`、`DOCKHOP_MIRROR` 三个，所有文件放在 `~/.dockhop`；链接改短（3.4.13）。
10. **精简（v1.1.4）**：用 DockHop 的人就是不想麻烦，平时用不上、或者容易用错的功能都去掉：`check`、`diagnose` 和菜单里的「收集诊断信息」、`in --file` 离线迁入、`out --no-stop`、`out --snapshot`、`out --workdir`、`in --skip-check`、`in --health-timeout`、`in --keep-files`、`-v`/`--verbose`、`DOCKHOP_KEEP_LOG`，以及对 bash 版旧链接的识别。保留 `--port`、`--host`、`DOCKHOP_HOME`、`DOCKHOP_MIRROR`、`DOCKHOP_NO_STATS`，以及给不能提问的场合用的 `--include`、`--stop-shared`、`--yes`、`--existing`、`--keep-succeeded`。附录里和 bash 版的对照表是重写时的记录，其中这些选项后来去掉了。
11. **按依赖顺序启动（v1.1.5）**：被用到的服务先启动，就绪后再启动用到它的。依赖除了 `--link` 等，还从环境变量和启动命令里认出写着的别的容器的名字。等多久按容器自己的健康检查设置；日志里记下顺序、每次健康检查的结果和容器最后的输出（见 3.4.2、3.4.9）。起因是用户迁移 1Panel 装的 Halo 时，Halo 先于它的数据库启动，迁入失败，而日志里看不出原因。v1.1.6 调整：依赖按强弱分三种，从配置里猜出来的只决定先后、等不到不拦着；创建也按依赖排序（见 3.4.2）。
12. **按几份独立审查修复（v1.1.6）**：逐条核对、能复现的先复现，按根本原因修，不加特判：项目目录在挂载目录里时检查用的配置文件单独打包（3.4.6）；启动依赖分强弱、创建按依赖排序、健康检查等待算上每次检查的时间（3.4.2）；检查全部挪到改动之前，`--rm`、Swarm 容器不能停这条规则迁出迁入共用，镜像名纳入事务，回滚资料确实写到磁盘（3.4.8）；迁移计划必须有，下载按计划限大小、核对校验值（3.4.13）；同一个服务的副本各自的改动分开恢复（3.4.2）；决定镜像来源时不再在多个协程里同时写一张表；按摘要固定的镜像本机已有时直接用；回滚时改回原名的旧容器可以重复补上网络；判断不了临时容器是谁的时候不删；停机打包大文件时 Ctrl+C 马上停；终端按键按完整的转义序列切分，Esc 和回车一起到也认得出，读按键不会卡住。只在非常少见的组合下出现、改动又大的几条当时暂不处理：回滚时跨项目借用网络的旧容器恢复顺序、新服务器用老的 docker-compose 1.x 且项目里部分容器停着、`include` 的 `project_directory` 用变量、预检和执行对替换集合的判断不完全一致（v1.1.8 都已修复，见下一条）。
13. **再按审查修复（v1.1.8）**：上一条暂不处理的几条都按根本原因修了：回滚时先全部放回、再按依赖统一启动（3.4.6）；服务的启动顺序加上容器之间的引用（3.4.2）；`include` 的变量目录提醒用户（3.4.2）；替换、保留哪些已有容器预检和迁入共用一条规则，改动已有服务之前再核对一次（3.4.8）。另外：回滚时只删这次迁入带来的镜像（3.4.8）；还原上次被中断的任务时按 Ctrl+C 也做完（3.4.6）；1.1.6 之前的旧服务器没有校验值，不再从它下载镜像（3.4.13）。每一处都有测试，并确认在修之前的代码上会失败。

## 附录 C：必须保留的事务和安全场景（来自 integration_docker.sh）

1. 迁移包里记录的系统路径（如 `/etc/localtime`）恢复时跳过，不能因此失败，更不能覆盖目标端文件
2. 替换已有容器时释放它占用的静态 IP；新容器失败后把旧容器的网络、IP、运行状态一并还原
3. 同名网络核心参数相同、只有标签不同时，提示并沿用
4. 同一台机器同时只允许一个恢复任务，第二个在改动任何东西之前退出
5. 挂载目录不能覆盖迁移包、事务记录或锁所在的目录（包括经过软链接父目录的情况）
6. 单个容器失败时，旧容器、卷、目录一起回滚
7. 原本停止的容器只创建、不启动
8. 没有健康检查的容器启动后立即退出，判为失败并保留旧容器
9. 卷和目录精确恢复：目标端多余的旧文件不能残留
10. 链接原样保留：外部、悬空、循环的软链接都不跟随
11. 单文件挂载、`/run` 下的 socket 路径
12. 数据写入失败时准确报告并回滚
13. 同名卷后端不同时，在清空之前就失败
14. 归档里有穿过软链接写出目标目录的成员时，在改动任何数据之前拒绝
15. Compose 新配置不健康时自动还原旧项目
16. `--existing fail` 在停止服务、覆盖数据之前终止
17. 回滚本身失败时，结果如实显示“回滚未完全成功”，不能误报“已安全回滚”
18. 新服务已验证、但清理回滚资料失败时，不能误报成功，也不能回滚已提交的数据
