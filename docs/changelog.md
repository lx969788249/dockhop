# DockHop 设计改动记录

现在是怎么设计的见 [design.md](design.md)，这里只记每个版本在设计上改了什么、为什么改。给用户看的更新说明在 GitHub 的发布页上（也写在 Git 的附注标签里）。

## 下一个版本（还没发布）

按第三份复核和自查整理结构（见问题表 J1–J7），每一步行为不变、单独提交。

- 事务日志每种改动一种记录：原地换内容（contents）和整个替换目录（bind）、只提交一部分（partial_commit）和全部提交（commit）以前各共用一种记录，靠备份目录在不在目录里面、Names 空不空来区分，改一处容易漏一处。现在各自单独记，每种记录要哪些字段都写在规则表里、写入前检查，穷尽测试覆盖每一种。以前的版本写的日志，读的时候在一处（upgrade）换成现在的记录。
- 迁过去之后容器应该是什么状态只有一份定义（`citem.want`，和旧服务器上一样）：启动哪些、等它就绪、提交前复查、结果摘要都按它判断。原来在运行的容器迁完自己退出了，哪怕退出码是 0 也算没成功：以前当成一次性任务正常做完，迁入照常提交、旧服务器结束传输，结果摘要还说服务在运行（第三份复核 A2）。建议里说明一次性任务怎么办。
- “谁在用这些数据”迁出迁入共用一套判断（`spec.WritesData`、`spec.UsesData`），以前两边各写一份、规则还不一样。迁出时只读挂载的容器不再一起停下：它改不了数据，以前挂着项目上级目录的 --rm 容器还会让整次迁出被拒（第三份复核 A8）；可写地挂着 /srv 这种系统目录、要打包的就在里面的，现在也一起停下，它照样能写进去（第三份复核 B5）。
- 迁入时临时停下和迁入的数据共用的已有容器，借用它的网络、进程空间的已有容器（例如 VPN 的边车）也一起停下，先停借用的、恢复时后启动，和它分在同一组：以前不停，被借用的一停它们就断了，恢复后也不会自己接回去（自查）。
- 换掉宿主机目录的两种办法（整个替换、原地换内容）各自的做、撤销、提交后清理放在一处（dirs.go），迁入时由一个地方选办法；以前分散在三个文件里。
- 要从旧服务器打包的每一处（挂载的目录、Compose 项目目录、项目目录外的文件、迁入前检查用的配置文件）都过同一个检查 approveRoot，各种路径的规则写在一张表里；以前四处各写各的，经过软链接指向上级目录的检查只有项目目录有。
- 项目目录外的文件、迁入前检查用的配置文件经过软链接指向项目目录（或者它自己）的上级目录时停下，指向系统路径的不打包：以前一个只查系统路径、一个什么都不查，软链接到上级目录会把整个项目连同旁边的项目打进迁移包，软链接到系统文件会把它的内容打进去（第三份复核 B4）。配置里直接写的上级目录（例如 build: ..）照样打包。
- 设计文档和改动记录里“指向系统目录就停下”改准确：按的是 `spec.IsSystemPath` 的名单，`/etc/nginx` 这种应用的配置目录不算（第三份复核 B6）。
- 用现在的版本恢复 v1.2.5 中断留下的日志时，原地换过内容的目录不再保持迁移过来的属主和权限：v1.2.5 没把目录本身原来的属性记进日志，而是把备份目录建成和它一样，读日志时从那里取回（第三份复核 A4）。
- 事务日志里有这个版本不认识的记录（多半是更新版本的 DockHop 写的）时，提示用最新版本运行，它会接着处理；以前当成日志损坏，让人手动处理、删掉回滚资料（第三份复核 A9）。

## v1.2.7

第三份复核发现，v1.2.6 为了让数据写到数据盘上，在新服务器上要写的目录路径本身是软链接时，会跟着它写到它指向的地方，而对指向的地方完全不检查：指向系统目录、上级目录或者一整块盘的根目录时，会把它们整个换成迁移过来的内容，提交后原来的就删了。能改这个路径所在目录的普通用户，可以在 root 迁入之前把它换成指向 /etc 的软链接。

改为这种路径不迁入：迁入前检查在下载之前停下，说出软链接指向哪里，提示怎么处理；真正写入之前再看一次，检查之后才被换成软链接的同样不迁入。跟随软链接的代码删掉了。数据要放在软链接指向的地方，可以删掉软链接后用 mount --bind 把那个目录挂过来（挂载点会在原地换内容）。有测试，并确认在修之前的代码上会失败。

## v1.2.6

第二份审查着重看结构，问题集中在迁入事务的日志和“同一件事写了几份”。先修缺陷，再整理结构。

修了这些缺陷：

- 日志按写法隐藏时，引号没有配对会把后面的日志一直吞到底，转义的引号后面的部分会漏出来（上一版引入）。改为只在一行里找，转义的引号算在值里，值后面紧跟的中文不算值。
- 判断挂载点时读不到挂载信息，当成了不是挂载点（上一版引入），于是按普通目录改名，正是上一版要修的“设备忙”。改为报错、停下。挂载信息里超长的一行（overlay 的 lowerdir）也能读了。
- 原地换内容时，目录本身的属性保不住：修改时间成功后成了操作的时间、回滚后成了回滚的时间，中途断电时回滚还会把权限改成 0700。现在目录本身原来的属主、权限、修改时间在动手之前记进日志，成功、回滚后都和应有的一样。
- 回滚时备份目录不在、数据盘又没挂上，会当成已经放回，删掉日志，原来的服务起在空目录上。现在停下说明、保留回滚资料；回滚换掉的整个目录时，那里是挂载点或者判断不了就不删。目录里东西很多时，回滚逐个比对原来有哪些东西很慢，改为查表。
- 目录里面还挂着别的磁盘时，整个替换会连带动到挂在里面的东西（实测会删掉那块盘上的文件）。现在迁入前停下。
- 新服务器上的路径本身是软链接（例如指向数据盘）时，会被换成普通目录，数据写到了系统盘上。现在解到它指向的目录里，软链接留着。
- 新服务器上的目录读不了（没有权限）时，迁入前没提示会被替换。现在读不了也算有东西。
- 项目目录经过软链接指向系统路径（`spec.IsSystemPath` 名单里的宿主机目录，例如 `/usr`；`/etc/nginx` 这种应用的配置目录不算）或者它自己的上级目录时，会把整个系统目录、别的项目和 DockHop 自己的文件一起打进迁移包，现在停下说明。项目外的文件是软链接、指向系统路径时，会把系统文件打进迁移包，现在和直接写系统路径一样不迁移。项目目录是软链接时，DockHop 自己的目录没有排除掉，现在按真实路径排除。
- 提交前再查一遍时，在重启、不健康的马上算失败，正常做完退出的一次性任务、Docker 偶尔回不了话也算失败。现在和等它就绪时用同一套判断：在重启、不健康的接着等它恢复，一次性任务正常做完算正常，读不到状态时重试。
- 接着做完上次只保留一部分服务的迁入之后，这次再取消或失败时，报告误称“没有改动”。
- 回滚重建原有的 Compose 容器时，固定的 MAC 丢了。
- 主目录写的是相对路径时，DockHop 自己的目录也是相对的，现在换成绝对路径；找不到主目录时说明原因。
- 新服务器上已经有指向迁移过来的目录的软链接、而这个目录的路径经过软链接（例如 `/srv` 指向数据盘）时，误报“指向不对”，迁入停下。
- Docker 不在本机时，只有跳过的容器用到的目录也会让迁入停下。

审查最后另外列了三个以前就有的问题，也修了：

- 迁出时，没选中、正在运行、挂载着要打包的 Compose 项目目录或者项目目录外的文件的容器，打包时没有一起停下（以前只比较数据卷和挂载目录），打包时它还在写。
- 迁出时要停哪些容器、恢复成什么状态，按读容器的时候的样子算：从读容器到停机，中间可能隔了好一会儿（选菜单、回答问题），这期间启动的共用数据的容器没停下，停下的容器打包完被启动起来，被重建的容器打包的是旧的配置。现在停机之前再核对一次，有变化就停下、什么都不动。
- 回滚按名字删这次新建的容器：建的时候名字被别的容器占着（创建失败），或者中断之后用户自己又建了同名的，会把别人的容器连同匿名卷一起删掉。现在建好就记下 ID，按 ID 删；没记下 ID 的（建好了还没来得及记就被强制结束，或者日志是升级之前的版本写的），只删在那之后才建的同名容器。

核对后不属实的：删除被替换的容器时，匿名卷还被别的容器用着会被删掉（实测 Docker 29.9 会留下它，另一个容器照常读写）。

每一处都有测试，并确认在修之前的代码上会失败；挂载点、软链接、嵌套挂载在 Docker 29.9 上用验收测试验证过。

整理了结构（行为不变，事务日志的格式不变）：

- 事务日志里每种记录要哪些字段、只保留一部分服务时算哪一边，集中在一张表里。写入前按表检查字段，读到不认识的记录当成日志损坏；回滚的每一遍都列全了不用管的记录，新加一种记录忘了处理时测试会失败。
- 只保留一部分服务的逻辑单独放在一个文件里。
- 解析软链接统一用一个函数（`host.RealPath`）；必须存在、读不到要报错的地方直接用 `filepath.EvalSymlinks`。
- “哪些事只能在 Docker 所在的机器上做”由迁入给出，迁入前检查按它停下；写数据卷时先不先清空也用同一条规则。以前检查里另写了一份清单。
- 读写数据卷的临时容器用哪个镜像、文件属性怎么记下和改回、容器眼下处在哪个阶段，各只留一份实现。
- 判断挂载点由调用方传进来，不再用只为测试替换的包级变量。

## v1.2.5

又一份审查逐条核对，属实的按根本原因修：

- 新服务器上同一个目录里已经有东西时，迁入前提示会被替换，和数据卷一样（以前一个字都不提）。
- 决定提交之前把就绪了的容器再查一遍：没有健康检查的容器稳定运行几秒就算就绪，之后还可能停掉，以前照样报成功。
- 目录本身是单独挂载的（例如一块数据盘）时，在原地换内容：不能改名，以前 Linux 报“设备忙”，迁入一定失败。解压用的临时目录先记进日志：以前程序被强制结束时它会留下来（隐藏的，可能很大）。
- 只保留一部分服务时，日志里记下保留下来的组：以前先把日志改成只剩没启动的组，这时被强制结束，保留下来那部分的回滚资料就再也找不到了。
- 恢复数据卷的临时容器从本机的镜像里挑：以前只从现有容器的镜像里挑，新服务器上一个容器都没有时恢复不了。
- 提交后删掉被替换的容器的匿名卷：以前留着，成了没人用的卷。
- 项目目录、项目外的文件本身是软链接时，打包它们指向的内容：以前项目目录什么都没打包，项目外的文件只打包了一个指向旧服务器路径的软链接，迁过去起不来。
- Docker 不在本机时，要替换已有的数据卷也在下载之前停下：以前要等下载完才失败。
- 手动指定的 MAC 地址也写进主网络的设置：接口 1.52（Docker 29）起读出来的容器配置里没有 MacAddress，新版本的接口创建时也只认网络设置里的，以前迁过去网卡用的是随机的 MAC。
- 日志按写法隐藏时遇到 & , ; 和引号里的空格也遮全：以前只遮了一半。
- 找不到主目录时不再退回 `/tmp`；预检读新服务器的情况时按 Ctrl+C 马上停下；改正设计文档里过时的说明（以前写的是没有权限时用 `sudo` 提权，并没有这样实现）。

核对后不属实的：非默认驱动的数据卷会被读成空卷（实测：用到时才挂载的卷，没启动过的临时容器照样能读能写）；一直重启的容器被当成已停止（实测 Docker 报的一直是在运行）。每一处都有测试，并确认在修之前的代码上会失败；挂载点、软链接的项目目录在真 Docker 上验证过。

## v1.2.4

三份审查逐条核对，属实的按根本原因修：

- 只保留一部分服务时，镜像名按创建容器实际用的名字算（用旧版本镜像的容器用的是 `dockhop-image:…`），按 Docker 的认法比较（`app` 和 `app:latest` 是同一个名字）：以前按配置里写的字符串比较，没保留的那组会把保留的那组也在用的名字改回去，或者该改回去的没改。
- 还原做完、回滚资料还没删除就被结束（比如断电）时，再还原不再删掉重建的原有 Compose 容器，也不再把数据卷改回去：以前下次会把原来的服务这期间写的数据改回去。重建的原有 Compose 容器记进日志，数据卷放回之后删掉备份。
- 标签里的 `run.sh` 落后一个版本（v1.2.1 时当作发布流程决定的）：以前先打标签、发布之后才更新 `run.sh`，改为先提交 `run.sh` 再打标签，已经发布的标签不动。更新说明改为运行发布工作流时填的说明。

核对后不属实的：再还原时原有 Compose 容器的匿名卷不会被 `-v` 删掉（在 Docker 29.9 上实测，按名字挂着的卷 Docker 不删）；统计用的 D1 表没有升级步骤不影响什么（线上的库上线 1.2.3 时已经加好 `failed` 列，`schema.sql` 是建新库用的）。每一处都有测试，并确认在修之前的代码上会失败。

## v1.2.3

用户想看软件稳不稳定、大家用的时候成功率怎么样：迁出、迁入失败时失败的次数加 1，只存这个数字；成功、失败的次数和成功率加了 `dockhop.run/stats` 这一页（以前只能在 Cloudflare 的 D1 里查，用户自己都看不到）。只迁入了一部分算失败，取消、中断不算；迁入、迁出各用一个结局，结果摘要和计数共用。已经提交、只是清理没做完的改为算成功（以前不算）。

## v1.2.2

用户问只拿到不带密钥的链接能不能下载，核实下来能（下到的是密文）：以前下载服务只看路径里的下载口令，用 `curl -k` 就能把迁移计划、迁移包和镜像文件下载走。改为旧服务器在握手时核对新服务器出示的、由密钥推算的证书，和新服务器核对旧服务器是同一套办法，所有地址都管得到；下载口令不再需要保密。有测试，并确认在修之前的代码上会失败。

## v1.2.1

逐条核对审查，属实的按根本原因修：

- 回滚时镜像名先改回、再删新加的：以前先删，它指向的镜像会被 Docker 一起删掉，而后面要改回去的名字原来正指向这个镜像，改不回去，原有的服务起不来。原有的镜像本来没有名字、迁入时加上的名字留着。镜像名按名字归组：以前按镜像算，两组用同一个镜像的不同名字时都算共用，没保留的那组的名字留了下来。
- 每个已有容器只跟着迁移包里的一部分走：以前属于迁移包里的项目、又和单独迁入的容器同名的已有容器两个都问，选得不一样时预检和迁入各按各的；都替换时它被改名备份、又随项目备份删除，回滚时找不到备份，按改过的名字重建。
- `--existing skip` 保留的服务不再检查端口、网络：以前照样检查，同名的服务占着自己的端口也报冲突，项目的端口 `--yes` 处理不了就取消了。
- 修的过程中发现：Compose 项目的容器（例如写了 `container_name` 的）和新服务器上无关的已有容器同名时，预检发现不了，要到建容器时才因为名字冲突整体回滚。现在这个已有容器跟着项目替换或保留，检查时就问。
- 迁入前用 Compose 检查配置改在决定替换、保留哪些已有服务之后做，不迁入的项目不检查。

核对后不属实的：回滚重建旧 Compose 容器时匿名卷不会丢（Docker 不删按名字挂着的卷，重建的容器照旧挂上）；标签里的 `run.sh` 落后一个版本当时认为是发布流程决定的（v1.2.4 改了）。每一处都有测试，并确认在修之前的代码上会失败。

## v1.2.0

传输改用 HTTPS：以前是明文 HTTP，迁移包和迁移计划本身虽然加密，路上能看到流量的人却能看到下载口令和迁入结果，可以照着口令把加密的文件下载走。证书由链接里的密钥推算，链接不变长；迁移包照旧用 age 加密；以前的 `http://` 链接提示在旧服务器上重新迁出。

## v1.1.8

把 v1.1.6 时暂不处理的几条都按根本原因修了：

- 回滚时先全部放回、再按依赖统一启动，排序跨项目、跨独立容器：以前按日志一条一条地放回、启动，一个项目借用另一个项目的容器的网络时，可能先重建、启动借用的那个而失败。
- 服务的启动顺序加上借用网络、`--link`、`--volumes-from` 的关系：老的 docker-compose 1.x 读不出 `depends_on`，以前这时会先启动借用别人网络的服务而失败。
- `include` 的 `project_directory` 用变量时提醒用户：以前悄悄按被包含文件的目录算，可能漏掉文件也不提醒。
- 替换、保留哪些已有容器，预检和迁入共用一条规则，改动已有服务之前再核对一次：以前预检认为属于别的项目的同名容器不会让出端口，平白给迁入的容器换了端口，选择保留它时也漏查共用数据。

另外：

- 回滚时只删这次迁入带来的镜像：加载镜像之前记下原有的镜像，回滚时先把镜像名全部改回去，最后只删迁入带来的、没有名字也没人用的。以前改回一个名字就按 ID 删它原来指向的镜像：原有的镜像只剩一个别的名字时会被连名字一起删，两个名字互换了指向时后面那个改不回去。
- 还原上次被中断的任务时，开始还原之后按 Ctrl+C 也做完再退出：以前当成“什么都没改动”的取消、删掉日志。
- “还没改动就取消”看用户有没有按 Ctrl+C，不看被打断的那一步返回什么错误：1.1.7 在检查环境、识别容器时按 Ctrl+C，会显示成“已中断”并留下日志。
- 1.1.6 之前的旧服务器没有校验值，不再从它下载镜像（镜像文件有好几个，被对调了发现不了）。

每一处都有测试，并确认在修之前的代码上会失败。

## v1.1.7

- 不在服务器上留没用的东西：以前迁移成功后还会留下空目录、锁文件和一份约 9MB 的程序，只是打开看看再取消也会留下日志。
- 迁移次数由 Worker 填进一行命令下载的 `run.sh`：从国内访问 `dockhop.run` 常常要好几秒（实测 2.5～14 秒），以前菜单最多等 1.5 秒去读，国内基本显示不出来；“加一”在结果显示完才发、只等 3 秒，国内大约一半没算上。现在“加一”在迁入提交成功时就在后台发出。

## v1.1.6

按几份独立审查修复：逐条核对、能复现的先复现，按根本原因修，不加特判。

- 项目目录在挂载目录里时，迁出时把 Compose 读配置要用的文件另外打包一份给检查用：以前这种项目在空的临时目录里检查，必然报“读不懂”，没法迁入。
- 启动依赖分强弱：v1.1.5 把认出来的依赖当成了必须等到的门槛，认错时可能卡住；改为从配置里猜出来的只决定先后、等不到不拦着。创建也按依赖排序：以前是“项目在前、独立容器在后、项目之间按名字”，一个项目用另一个项目建的网络（反向代理的常见写法）、或者借用独立容器的网络时会创建失败。健康检查等待算上每次检查本身的时间。
- 检查全部挪到改动之前；`--rm`、Swarm 容器不能停这条规则迁出迁入共用；镜像名纳入事务：以前镜像在事务开始前就加载、加名字，迁入失败后新服务器上原有的同名镜像名仍指向旧服务器的版本。
- 回滚资料确实写到磁盘：以前备份只写进了缓存，断电后可能只剩半份，而原件已经被替换了。停机记录读不懂时保留并说明，不再当作没有。
- 迁移计划必须有：以前没有它会跳过全部检查、直接替换同名服务。下载按计划限大小、核对校验值：以前一直写到对方停止发送，网络上的设备可以把磁盘写满。
- 镜像只承载删除，新增和修改的文件按容器分别写进去：以前把每个副本的改动连同删除一起做成镜像、再按服务覆盖，最后一个副本的镜像会被所有副本用上，其他副本的改动静默丢失。
- 另外：决定镜像来源时不再在多个协程里同时写一张表；按摘要固定的镜像本机已有时直接用；回滚时改回原名的旧容器可以重复补上网络；判断不了临时容器是谁的时候不删；停机打包大文件时 Ctrl+C 马上停；终端按键按完整的转义序列切分，Esc 和回车一起到也认得出，读按键不会卡住。
- 更新说明开始写在附注标签里。

只在非常少见的组合下出现、改动又大的几条当时暂不处理（v1.1.8 都修了）：回滚时跨项目借用网络的旧容器恢复顺序、新服务器用老的 docker-compose 1.x 且项目里部分容器停着、`include` 的 `project_directory` 用变量、预检和执行对替换集合的判断不完全一致。

## v1.1.5

按依赖顺序启动：被用到的服务先启动，就绪后再启动用到它的。依赖除了 `--link` 等，还从环境变量和启动命令里认出写着的别的容器的名字。起因是用户迁移 1Panel 装的 Halo 时，Halo 先于它的数据库启动：v1.1.4 及以前按项目名一个一个“启动并等就绪”，先启动的 Halo 找不到还没启动的数据库，等到超时，整个迁入回滚，而日志里看不出原因。

- 等多久按容器自己的健康检查设置，等到 Docker 判它不健康的时候再多 30 秒：以前只等到第一次检查跑完，Halo 是 95 秒，而 Docker 自己要三四分钟才下结论。
- 等容器就绪时，日志里记下顺序、状态的变化、每次健康检查的结果和容器最后 100 行输出：以前只留最后 5 行、报错里接最后一行，Java 应用报错时正好是一行调用栈，看不出原因；建议里的 `docker compose logs` 在回滚之后也用不了。

## v1.1.4

精简：用 DockHop 的人就是不想麻烦，平时用不上、或者容易用错的功能都去掉了：

- `check`（`in` 本来就先检查，有问题在改动之前停下）、`diagnose` 和菜单里的「收集诊断信息」（失败时保留的日志里记着系统和 Docker 的情况）；
- `in --file` 离线迁入（只有旧服务器在内网时才用得上，手动拷文件、敲长命令和“不想麻烦”相反）；
- `out --no-stop`、`out --snapshot`、`out --workdir`（和 `DOCKHOP_HOME` 重复）、`in --skip-check`、`in --health-timeout`、`in --keep-files`、`-v`/`--verbose`、`DOCKHOP_KEEP_LOG`（测试用的改名为 `DOCKHOP_TEST_KEEP_LOG`）；
- 对 bash 版旧链接的识别，按链接格式不对处理。

镜像改为每个单独导出成一个加密文件（迁移包格式版本 2），新服务器在下载之前逐个决定从哪里来；以前所有镜像都在迁移包里。
